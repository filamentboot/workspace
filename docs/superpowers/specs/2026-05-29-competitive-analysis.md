# FilamentAdmin 对标 FastAdmin 的差距分析

> 基于 2026-05-29 调研整理，当前仅保留 FastAdmin 作为功能丰富度对照基准。

---

## 一、对照基准总览

| 产品 | 官网 | 演示站 | 账号 / 密码 | 文档 | Git | Stars | 技术栈 |
|------|------|--------|------------|------|-----|-------|--------|
| **FastAdmin** | fastadmin.net | https://demo.fastadmin.net/admin.php | admin / 123456 | doc.fastadmin.net | github.com/fastadminnet/fastadmin | ~1.9k | ThinkPHP + Bootstrap/jQuery |
| **FilamentAdmin**（我们） | http://filamentadmin.local/ | 暂无 | admin / password | docs/features/authentication.md | — | — | Laravel 13 + Filament 5 |

> 注：
> - FastAdmin 仍然是国内后台基础平台里最强的功能丰富度参照。
> - FilamentAdmin 的价值，不是复制它的技术栈，而是用 Laravel + Filament 提供同等级别的后台底座能力。

### 2.8 核心差距

1. **权限与菜单仍是体感最大的差距**
   FastAdmin 默认安装后最显性的能力就是权限树和菜单树。我们已经有权限基础，但菜单管理还没开始做，这会直接影响“像不像一个后台底座”的第一印象。

2. **系统配置与附件管理仍然缺位**
   FastAdmin 的配置和附件能力都属于一眼可见的通用后台能力。我们目前这两块都还没落地，会让用户觉得项目骨架有了，但可运营性不足。

3. **插件中心必须尽早出现**
   插件系统是 FilamentAdmin 的长期特色，但如果第一版迟迟看不到本地插件中心入口，用户很难建立“这是一个有代码市场潜力的平台”的认知。

4. **CRUD 体验需要用规范补齐**
   我们不一定要复制 FastAdmin 的生成器形态，但至少要把 Filament 官方生成命令与项目的 Policy、Resource、基类约定整合起来，形成真正可复制的开发规范。

## 三、核心结论

### 1. 定位

FilamentAdmin 的目标，不是复制 FastAdmin 的技术栈或界面风格，而是用 Laravel + Filament 做出同等级别的后台基础平台能力。

### 2. 阶段优先级

最影响用户感知的，不是第二版商业化设想，而是第一版里权限、菜单、配置、日志、附件这几块基础后台能力能否尽快补齐。

### 3. 插件系统节奏

插件市场是长期差异化方向，但第一步应该先落地“本地插件中心 + 启停 + 配置入口”，先建立入口感，再谈远程市场和商业化。

---

## 四、建议

1. Phase 2 继续把权限体系做完整，重点补齐围绕业务 Resource 的权限点生成与整理规范。
2. Phase 3 需要优先落地菜单管理和系统配置，这两块对“后台基座完成度”的提升最直观。
3. 操作日志和附件管理应紧随其后，它们是用户最容易感知到的运营能力。
4. 插件中心 MVP 不要拖到太后面，哪怕第一版只能展示已安装插件列表和启停按钮，也值得先落地。
5. 所有文档继续坚持“目标状态”和“当前代码状态”分开写，避免未来再出现完成度口径漂移。

## 五、首批开发插件规划

以下按 FastAdmin 插件市场下载量与业务刚需程度排序，结合双轨制架构（工具型 `package` / 业务型 `module`）规划首批插件：

| 插件名称 | 类型 | 核心功能 | 开发优先级 | 备注 |
|----------|------|----------|-----------|------|
| **云存储 (OSS/S3)** | 工具型 | 替换本地存储，支持阿里云/腾讯云/AWS S3，自动缩略图生成 | P0 | 任何项目必装，走 `vendor/` Composer 包 |
| **短信发送** | 工具型 | 阿里云/腾讯云短信接口，支持验证码、通知模板、发送记录 | P0 | 登录验证/订单通知刚需，配置即用的 Settings 类 |
| **Excel 导入导出** | 工具型 | 复杂表格数据导出/导入，支持自定义模板、批量处理、进度提示 | P0 | 运营人员高频使用，基于 `maatwebsite/excel` 封装 |
| **第三方登录** | 工具型 | 微信/QQ/微博 OAuth 登录后台或前台会员，支持账号绑定 | P1 | 降低注册门槛，走 `laravel/socialite` 封装 |
| **支付模块** | 工具型 | 微信支付/支付宝集成，支持扫码/H5/JSAPI，订单回调与对账 | P1 | 电商/知识付费项目刚需，配置化路由与回调处理 |
| **富文本编辑器** | 工具型 | UEditor / TinyMCE / Tiptap 集成，自动适配 Media Library 图片上传 | P1 | 内容管理/公告发布必备，替代原生 textarea |
| **会员管理扩展** | 业务型 | 前台会员等级/积分/余额管理，消费记录与权益分配 | P2 | 解包至 `Modules/Member`，代码归项目所有，方便二开 |
| **数据回收站增强** | 业务型 | 全局软删除数据查看、对比、批量恢复与彻底清理 | P2 | 跨模块通用能力，可作独立工具包或轻量业务模块 |

### 插件开发原则

1. **工具型优先**：P0/P1 插件全部采用 `package` 模式，安装后配置即用，不侵入业务代码。
2. **配置驱动**：所有插件必须声明自己的 `Settings` 类，插件中心自动渲染配置页，避免重复开发设置界面。
3. **权限接入**：插件注册的路由/Resource 必须接入 Filament Shield 权限体系，不得绕过角色检查。
4. **文档配套**：每个插件需包含 `README.md`（安装/配置/升级指南）与基础 Pest 测试，符合上架品质门槛。
