## 1. 执行摘要

本期目标不是继续扩展功能，而是把 FilamentAdmin 整理成一个 **可以独立发布的 Composer Library 包**，并完成一次真实可执行的对外发布演练。

> 2026-06-03 结构修正：当前仓库根目录重新定义为演示项目，真正发布对象调整为子目录包 `packages/filament-admin/`，对外通过 split 推送到 GitHub / Gitee 包仓库。

本次发布链路有三个硬目标：

1. 主包 **彻底摆脱 `PluginPlatform`**
2. 当前运行型应用 **保留为演示项目根仓库**
3. 主包完成 **GitHub Release + Packagist 接入并验证安装**

本文不是泛泛而谈的功能需求文档，而是一次完整发布演练的 SOP。维护者应能按本文顺序执行，从仓库收口一路推进到 Packagist 安装验证。

## 2. 发布目标与本次范围

### 2.1 发布目标

本次发布完成后，FilamentAdmin 需要满足以下状态：

- 公开主仓库为 GitHub 包仓库：`https://github.com/john-captain/filament-admin`
- 当前主包不再以内置方式承载 `PluginPlatform`
- 当前根仓库保留演示项目职责，主包改为子目录包
- 仓库内容、Composer 元数据、README、安装文档、CHANGELOG、升级说明全部以“独立包”视角表达
- 已完成一次正式版本发布
- 已接入 Packagist，并验证 `composer require laravelstack/filament-admin` 可用

### 2.2 本次范围

本次必须完成：

- `PluginPlatform` 剥离
- 子目录包建立与收口
- 演示项目与主包边界修正
- 发布资料收口
- GitHub Tag / Release
- Packagist 提交、自动更新配置、安装验证

### 2.3 不在范围内

本次不处理：

- 插件市场业务能力推进，归 `06-插件市场.md`
- 第二版运维平台能力
- 演示站业务功能规划
- 商业化插件分发、异步安装、插件升级闭环

## 3. 发布前硬约束

在进入发布演练前，必须同时满足以下约束：

### 3.1 发布对象约束

- 本次发布对象是主包 `laravelstack/filament-admin`
- 本次发布对象不是演示站
- 本次发布对象不包含 `PluginPlatform`

### 3.2 仓库约束

- GitHub 包仓库是唯一正式发布源
- 所有 Tag、Release、CHANGELOG、README 最终以 GitHub 包仓库为准
- 主包仓库只保留包发布所需内容，不再混入演示站专属部署语义

### 3.3 文档约束

- 所有对外文档必须使用“独立包”口径
- 不得把规划能力写成已完成
- 不得再把 `PluginPlatform` 写成当前主包仓库的内置组成部分

### 3.4 Packagist 约束

- Packagist 不是“后续准备项”，而是本次发布必须完成项
- 最终验收必须包含实际安装验证

### 3.5 发布前资源与权限清单

在开始执行发布演练前，维护者必须确认以下资源和权限已经具备：

| 资源/权限 | 说明 | 检查标准 |
|-----------|------|---------|
| GitHub 包仓库管理权限 | 需要创建 Tag、Release、修改默认分支设置、调整仓库说明 | 能正常访问并执行发布动作 |
| Packagist 账号/组织权限 | 需要提交包、查看同步状态、配置自动更新 | 能登录并提交目标仓库 |
| 演示站仓库写权限 | 需要迁移当前运行型应用并持续维护 | 能向独立演示站仓库推送代码 |
| 主包仓库写权限 | 需要收口包结构、改文档、调整 Composer 元数据 | 能向主包仓库推送变更 |
| 干净安装验证环境 | 需要验证 `composer require laravelstack/filament-admin` | 能在无历史残留环境中执行安装 |
| 仓库映射关系 | 需要明确当前本地仓库、GitHub 包仓库、演示站仓库之间的对应关系 | 执行前有书面记录可核对 |

若以上任一项缺失，本次发布演练不得开始。

## 4. 完整发布演练流程

以下步骤按顺序执行，不建议跳步。

### 4.0 阶段性放行条件

完整发布流程不是一条可以硬推到底的流水线，每个阶段结束后都需要满足放行条件，才允许进入下一步。

| 阶段 | 放行条件 | 未满足时的处理 |
|------|---------|---------------|
| `PluginPlatform` 剥离完成 | 主包已从 Composer、运行时、测试、目录和文档中彻底解耦 | 禁止进入演示站拆分和正式发布阶段 |
| 演示站拆分完成 | 演示站可在独立仓库继续维护，主包仓库不再承担运行站点职责 | 禁止宣称主包仓库已独立 |
| 主包结构与文档收口完成 | 包结构、README、安装文档、CHANGELOG、升级说明口径一致 | 禁止创建正式 Tag |
| GitHub Release 完成 | Tag、Release Notes、仓库内容一致 | 禁止推进 Packagist 对外宣发 |
| Packagist 安装验证完成 | `composer require laravelstack/filament-admin` 实际成功 | 禁止宣称“发布完成” |

任何阶段若未达到放行条件，必须先修正当前阶段问题，再继续后续步骤。

### 4.1 第一步：剥离 PluginPlatform

**目标**

先把主包从 `PluginPlatform` 的依赖、目录、运行时接入、测试和文档口径中彻底解耦，建立清晰发布对象。

**输入**

- 当前主包仓库代码
- 当前 `composer.json`
- 当前 `packages/plugin-platform/`
- 当前主包运行时代码、测试和文档

**操作**

1. 从 `composer.json` 中移除 `filament-admin/plugin-platform`
2. 从 `composer.json` 中移除指向 `packages/plugin-platform` 的本地 `path repository`
3. 清理主包运行时代码中的 `PluginPlatform` 资源发现、导航接入、命名空间引用
4. 清理主包测试集中所有 `PluginPlatform` 相关测试
5. 清理仓库内置的 `packages/plugin-platform/`
6. 清理主包 README / wiki / PRD 中将 `PluginPlatform` 描述为当前仓库内置能力的表述

**产出**

- 主包不再依赖 `PluginPlatform`
- 主包不再内置 `PluginPlatform`
- 主包不再通过运行时逻辑接入 `PluginPlatform`

**检查点**

- `composer.json` 不再出现 `filament-admin/plugin-platform`
- `composer.json` 不再出现 `packages/plugin-platform`
- 主包运行时代码不再出现 `FilamentAdmin\\PluginPlatform`
- 主包测试集中不再保留 `PluginPlatform` 测试套件
- 仓库中不再保留 `packages/plugin-platform/`

**失败处理**

- 若主包关键运行逻辑仍依赖 `PluginPlatform`，立即停止进入下一步
- 回退到“先解耦再发布”的原则，不允许带残留耦合进入发布阶段

**放行条件**

- 满足 `4.0` 中关于 `PluginPlatform` 剥离完成的全部要求

### 4.2 第二步：拆出演示站

**目标**

把当前运行型 Laravel 应用迁移到独立演示站仓库，停止让主包仓库承担演示站职责。

**输入**

- 当前本地运行型应用代码
- 独立演示站仓库

**操作**

1. 创建或确认独立演示站仓库可用
2. 将当前以运行站点为主的应用形态迁移到演示站仓库
3. 将演示站专属内容从主包仓库移出，包括部署脚本、域名假设、演示账号机制、数据重置机制等
4. 主包仓库只保留发布独立包所需内容

**产出**

- 演示站仓库独立存在
- 主包仓库不再被当作运行站点仓库使用

**检查点**

- 演示站可在独立仓库继续维护
- 主包仓库目录和文档不再以“可直接部署站点”为主叙述

**失败处理**

- 若演示站仍依赖主包仓库中的专属文件，暂停下一步
- 先补齐演示站仓库再继续发布主包

**放行条件**

- 满足 `4.0` 中关于演示站拆分完成的全部要求

### 4.3 第三步：确认发布对象

**目标**

明确本次发布的对象、边界和仓库内容，防止后续文档与发布动作跑偏。

**输入**

- 已剥离 `PluginPlatform` 的主包仓库
- 已拆出的演示站仓库

**操作**

1. 明确主包名称为 `laravelstack/filament-admin`
2. 明确主包定位为 Composer Library 包
3. 明确本次不发布演示站
4. 明确本次不发布 `PluginPlatform`
5. 明确主包仓库的保留范围：`src/`、`config/`、`database/`、`resources/`、`stubs/`、`wiki/`、`tests/`、发布资料

**产出**

- 发布对象边界清晰

**检查点**

- 主包定位、目录边界、发布对象在文档中表述一致

**失败处理**

- 若仍存在“这是站点项目还是包仓库”的歧义，暂停下一步

**放行条件**

- 主包定位、发布对象、目录边界在仓库与文档中无冲突

### 4.4 第四步：准备公开主仓库

**目标**

确认 GitHub 包仓库成为唯一正式发布源，并统一后续发版入口。

**输入**

- GitHub 包仓库：`https://github.com/john-captain/filament-admin`

**操作**

1. 确认 GitHub 包仓库地址正确
2. 确认默认分支、仓库名称、仓库说明与主包定位一致
3. 确认后续 Tag 与 Release 均在 GitHub 包仓库执行
4. 确认 README 首页将以 GitHub 仓库为唯一正式入口

**产出**

- 对外发布入口唯一化

**检查点**

- 文档和发布动作不再指向其他主入口

**失败处理**

- 若发布入口仍多头并存，先统一入口再继续

**放行条件**

- GitHub 包仓库已成为唯一正式发布入口

### 4.5 第五步：收口包结构

**目标**

把仓库结构收口到符合 Library 包定位的最小可发布形态。

**输入**

- `docs/prd/01-项目规范与目录结构.md`
- 当前主包目录结构

**操作**

1. 对齐 `src/` 作为主包核心源码目录
2. 对齐 `config/`、`database/`、`resources/`、`stubs/`、`wiki/` 的职责
3. 停止在 `app/` 下继续扩展属于主包核心的类
4. 复核 ServiceProvider、Plugin、迁移、语言包、stubs 是否在正确位置
5. 清理仅服务运行站点、而不服务包发布的残留内容

**产出**

- 主包目录结构符合独立包定位

**检查点**

- 主包核心代码不再继续新增到 `app/`
- 目录职责与 `01-项目规范与目录结构.md` 一致

**失败处理**

- 若关键核心能力仍只能依赖 `app/` 语义存在，暂停发布并先补结构迁移

**放行条件**

- 主包结构已达到最小可发布形态

### 4.6 第六步：收口发布资料

**目标**

让外部开发者在第一次访问仓库时，能准确理解项目定位、安装方式和当前边界。

**输入**

- README
- 安装文档
- CHANGELOG
- 升级说明
- LICENSE
- wiki 文档

**操作**

1. 重写 README 为独立包视角
2. 完善安装文档，写清环境要求、初始化方式、当前限制
3. 补齐 CHANGELOG
4. 补齐升级说明
5. 保证 LICENSE 完整
6. 统一项目概览、安装文档、PRD 中的状态描述

**产出**

- 一套可公开展示的发布资料

**检查点**

- README 首屏能说明“是什么、怎么装、现在做到哪一步”
- 文档不再混入演示站专属语义
- 文档不再把 `PluginPlatform` 说成当前主包仓库的内置能力

**失败处理**

- 若文档仍有明显夸大或边界混淆，停止正式发布

**放行条件**

- 满足 `4.0` 中关于主包结构与文档收口完成的全部要求

### 4.7 第七步：执行正式发布

**目标**

在 GitHub 包仓库完成一次真实的版本发布。

**输入**

- 已收口的主包仓库
- 版本号
- CHANGELOG / Release Notes 草稿

**操作**

1. 确认版本号遵循 SemVer 风格
2. 更新 CHANGELOG
3. 创建 Git Tag
4. 推送 Tag
5. 在 GitHub 创建 Release
6. 写清本次 Release Notes，包括新增、修复、限制、已知边界

**产出**

- 一个正式可追溯的 GitHub 发布版本

**检查点**

- Tag 存在且可追溯到对应代码
- GitHub Release 内容与仓库状态一致

**失败处理**

- 若发布说明与实际内容不一致，不应继续对外宣传
- 必要时删除错误 Tag / 重建 Release，再重新执行

**放行条件**

- 满足 `4.0` 中关于 GitHub Release 完成的全部要求

### 4.8 第八步：接入并验证 Packagist

**目标**

完成 Packagist 接入，并验证主包可以通过 Composer 正常安装。

**输入**

- GitHub 包仓库
- 已发布版本 Tag

**操作**

1. 在 Packagist 提交 GitHub 包仓库
2. 配置包更新同步机制
3. 等待或触发首轮同步
4. 使用一个干净环境执行 `composer require laravelstack/filament-admin`
5. 验证安装结果与文档一致

**产出**

- Packagist 上的主包条目
- 可实际安装的主包

**检查点**

- Packagist 能识别该包
- `composer require laravelstack/filament-admin` 实际成功
- 安装结果与 README / 安装文档描述一致

**失败处理**

- 若 Packagist 识别失败或安装失败，本次发布不得视为完成
- 需回到前置步骤修正 Composer 元数据、仓库结构或发布内容后重新验证

**放行条件**

- 满足 `4.0` 中关于 Packagist 安装验证完成的全部要求

### 5.1 剥离范围

- Composer 依赖
- 本地 path repository
- 运行时代码引用
- Panel 资源发现
- 导航入口
- 测试套件

### 5.2 剥离验收

- 主包 `composer.json` 不再依赖 `filament-admin/plugin-platform`
- 主包仓库不再保留 `packages/plugin-platform/`
- 主包运行时代码中不再引用 `FilamentAdmin\\PluginPlatform`
- 主包测试集中不再包含 `PluginPlatform` 相关测试
- 主包文档中不再把 `PluginPlatform` 作为当前仓库内置能力描述

## 6. 回滚与失败处理

若发布过程中任一步骤失败，按以下原则处理：

### 6.1 发布前失败

- 若失败发生在正式打 Tag 前，优先修正仓库内容，不对外发布

### 6.2 发布后失败

- 若已创建 GitHub Release，但 Packagist 接入或安装验证失败，则本次发布不得宣称“可安装”
- 必要时撤回错误说明，修正后重新发版

### 6.3 原则

- 不允许带 `PluginPlatform` 残留耦合进入正式发布
- 不允许在 Packagist 安装未通过时宣称发布已完成
- 不允许把演示站问题转嫁为主包发布问题

## 7. 命名规范与安装验证口径

为避免发布过程中出现多人各写各的情况，本次发布链路统一以下命名与验证规则。

### 7.1 版本号规范

- 使用 SemVer 风格版本号
- 首个可公开验证的发布版本应采用清晰的预发布或正式版本标记
- 不再使用带中文能力名、临时说明或阶段备注的 Tag 命名方式

### 7.2 Git Tag 规范

- 推荐格式：`vX.Y.Z`
- 若为预发布版本，可使用：`vX.Y.Z-beta.N`、`vX.Y.Z-rc.N`
- 同一语义版本只能保留一个正式 Tag，不得重复指向不同提交

### 7.3 GitHub Release 规范

- Release 标题必须与 Tag 对齐
- Release Notes 至少包含：
  - 本次新增
  - 本次修复
  - 本次限制
  - 已知边界
- 不得在 Release Notes 中宣称未完成能力已可用

### 7.4 CHANGELOG 规范

- 每次发布必须在 CHANGELOG 中有对应版本段落
- 建议至少包含：
  - Added
  - Changed
  - Fixed
  - Known Limitations
- CHANGELOG 与 GitHub Release 描述必须保持一致，不允许各写一套

### 7.5 Packagist 元数据规范

- 包名必须为：`laravelstack/filament-admin`
- `description` 必须是独立包定位表述
- `license` 必须明确
- `homepage`、`support`、`keywords`、`authors` 必须完整
- 不得保留 Laravel Skeleton 默认元数据

### 7.6 安装验证环境口径

安装验证必须在**干净环境**中执行，不能复用当前长期开发环境作为最终验收依据。

干净环境至少满足：

- 没有历史 `vendor/`
- 没有旧版 `filament-admin/filament-admin` 安装坐标残留
- 没有本地 path repository 残留
- 没有 `PluginPlatform` 本地联调依赖残留

### 7.7 安装验证步骤口径

安装验证至少覆盖：

1. 执行 `composer require laravelstack/filament-admin`
2. 校验依赖解析成功
3. 校验包可被自动发现或按文档完成注册
4. 校验基础迁移、配置发布或安装文档要求的初始化步骤可执行
5. 校验核心后台入口符合文档说明

### 7.8 安装验证成功标准

以下条件需同时满足，才可视为安装验证通过：

- `composer require laravelstack/filament-admin` 无依赖冲突
- 安装后目录结构与文档描述一致
- 包注册方式可执行
- 初始化步骤无阻断性错误
- 关键后台能力至少达到“可安装、可进入、可继续初始化”的状态
