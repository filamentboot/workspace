## 1. 项目定位

### 1.1 执行摘要

FilamentAdmin 是一个 **Composer Library 包**，通过 `composer require laravelstack/filament-admin` 安装到现有 Laravel 项目，提供可安装、可登录、有基础权限管理的后台 MVP，包含管理员认证、角色权限、菜单管理、登录日志、操作日志、部门管理、个人资料页、后台首页等核心能力。

### 1.2 谁有这个问题?

独立开发者和小团队启动新项目时,需要从零搭建后台基础能力(登录、权限、菜单、日志),耗费 1-2 周时间。

### 1.3 问题是什么?

每个新项目都要重复解决:
- 管理员认证(username/email 登录、2FA、登录限流)
- 角色权限体系(RBAC、菜单权限、数据权限)
- 后台导航和菜单管理
- 操作日志和审计追踪

### 1.4 为什么痛苦?

- 时间成本:1-2 周重复搭建
- 质量风险:容易引入安全漏洞
- 维护负担:各项目后台代码各自演进

### 1.5 目标用户

**主要角色:独立开发者小李**
- 全栈开发者,接外包项目或做 SaaS 产品
- 目标:快速交付项目,减少重复开发时间
- 痛点:每次新项目都要重新搭建后台

**Jobs-to-be-Done**:
> "当启动新项目时,我想要一套完整的后台基础能力,这样我可以直接开始写业务代码。"

## 2. 架构模式与目录结构

### 2.1 架构模式：Library 包

本项目采用 **Library 包** 模式交付，与 `laravel-admin`、`filament` 本身的交付方式一致。

- **交付物**：一个标准的 Composer 包，发布到 Packagist。
- **安装方式**：用户通过 `composer require laravelstack/filament-admin` 安装到现有 Laravel 项目。
- **代码位置**：包代码位于用户项目的 `vendor/laravelstack/filament-admin/src/` 下，用户不直接修改。
- **命名空间**：`FilamentAdmin\`。

**与 Skeleton 模式的核心区别：**

| 维度 | Skeleton | Library（本项目） |
|------|----------|-----------------|
| 安装命令 | `composer create-project` | `composer require` |
| 代码归属 | 用户拥有，可直接改 | 在 vendor/，用户不改 |
| 升级方式 | 手动同步 | `composer update` |
| 自定义方式 | 直接改文件 | 继承扩展 + 发布 stub |

**注册方式：** 用户在自己的 `AdminPanelProvider` 中显式注册 Plugin：

```php
use FilamentAdmin\FilamentAdminPlugin;

->plugins([
    FilamentAdminPlugin::make(),
])
```

**自定义方式：** 用户如需覆盖默认行为，通过 Artisan 命令生成扩展 stub：

```bash
# 发布单个扩展
php artisan filament-admin:publish --model=AdminUser
php artisan filament-admin:publish --resource=AdminUserResource

# 发布全部扩展
php artisan filament-admin:publish --all
```

执行后在用户的 `app/` 下生成继承类，用户在子类中自定义，然后通过 Plugin API 显式绑定，告知包使用用户的类：

```php
FilamentAdminPlugin::make()
    ->adminUserModel(\App\Models\AdminUser::class)
    ->adminUserResource(\App\Filament\Resources\AdminUserResource::class)
```

未绑定的类自动使用包内默认实现，无需全部发布。

**Plugin API 完整绑定规范：**

所有可替换的 Model 和 Resource，Plugin 均提供对应的绑定方法。命名约定：

- **Guard 配置**：`->guard(string $guardName)`（默认为 `admin`，与 `config/filament-admin.php` 的 `guard` 键同步）
- **Model 绑定**：`->{驼峰模型名}Model(string $class)`
- **Resource 绑定**：`->{驼峰Resource名}Resource(string $class)`（去掉 `Resource` 后缀再驼峰）

完整示例（基于 PRD02 完成后的实际类清单）：

```php
FilamentAdminPlugin::make()
    ->guard('admin')                                              // Guard 配置
    ->adminUserModel(\App\Models\AdminUser::class)               // 替换 AdminUser 模型
    ->departmentModel(\App\Models\Department::class)             // 替换 Department 模型
    ->loginLogModel(\App\Models\LoginLog::class)                 // 替换 LoginLog 模型
    ->menuModel(\App\Models\Menu::class)                         // 替换 Menu 模型
    ->adminUserResource(\App\Filament\Resources\AdminUserResource::class)
    ->departmentResource(\App\Filament\Resources\DepartmentResource::class)
    ->loginLogResource(\App\Filament\Resources\LoginLogResource::class)
    ->menuResource(\App\Filament\Resources\MenuResource::class)
```

新增可扩展类时，`FilamentAdminPlugin.php` 必须同步新增对应的绑定方法，不可只在包内使用而不暴露给用户。

> - `app/Models/User.php`：Laravel 默认 users 表模型，不属于本包

#### 2.2.2 用户项目结构（安装后）

用户通过 `composer require` 安装后，自己的项目结构如下：

```text
user-project/
├── app/
│   ├── Models/
│   │   └── AdminUser.php        # (可选) 继承 FilamentAdmin\Models\AdminUser
│   └── Filament/
│       └── Resources/
│           └── AdminUserResource.php  # (可选) 继承包内 AdminUserResource
├── config/
│   └── filament-admin.php       # (可选) vendor:publish 后自定义配置
├── bootstrap/
│   └── providers.php            # FilamentAdminServiceProvider 自动注册
└── app/Providers/Filament/
    └── AdminPanelProvider.php   # 用户在此注册 FilamentAdminPlugin::make()
```

**关键规范：**
1. **包源码**：全部位于 `src/` 下，命名空间 `FilamentAdmin\`，不使用 `App\`。
2. **Plugin 入口**：`FilamentAdminPlugin.php` 是用户与包交互的唯一入口，功能开关和模型绑定均通过 Plugin API 配置。
3. **内置 Models**：位于 `src/Models/`，用户可通过 `filament-admin:publish --model=Xxx` 生成继承类后覆盖。
4. **内置 Resources**：位于 `src/Filament/Resources/`，用户可通过 `filament-admin:publish --resource=Xxx` 生成继承类后覆盖。
5. **角色管理 Resource**：由 `bezhansalleh/filament-shield` 包自带，**禁止**在包内手写 `RoleResource`。
6. **Policies**：位于 `src/Policies/`，与 Model 对应，命名 `{Model}Policy`。
7. **Enums**：位于 `src/Enums/`，替代魔法字符串。
8. **Listeners**：位于 `src/Listeners/`，在 `FilamentAdminServiceProvider` 中注册。
9. **Observers**：位于 `src/Observers/`，在 `FilamentAdminServiceProvider::boot()` 中注册。
10. **Commands**：位于 `src/Commands/`，在 `FilamentAdminServiceProvider` 中注册，调度配置由用户项目的 `routes/console.php` 管理。
11. **Migrations**：位于 `database/migrations/`，由 `FilamentAdminServiceProvider` 通过 `loadMigrationsFrom()` 自动加载，用户无需手动发布。
12. **Stubs**：位于 `stubs/`，供 `filament-admin:publish` 命令使用，每个可扩展类对应一个 `.stub` 文件。
13. **Services**：复杂业务逻辑抽离到 `src/Services/`（见规范 2.3）。

### 2.3 Services 使用边界

`src/Services/` 用于承载**不属于单一 Model 或 Resource**、且**包含复杂业务逻辑**的代码。

**应该放入 Service 的情况：**
- 跨多个 Model 的业务编排（如 `DepartmentTree`：递归构建部门树、计算子孙节点）
- 需要在包内多处复用的逻辑（如 `DataScopeResolver`：根据角色数据权限范围过滤查询）
- 封装外部系统交互（如 `AdminNavigationBuilder`：构建后台导航菜单）

**不应该放入 Service 的情况：**
- 单条记录的 CRUD 操作 → 直接在 Resource 或 Model 中处理
- 只在一个 Resource 内使用的逻辑 → 放在该 Resource 对应的 Action 或 Form 方法中
- 简单的数据格式化 → 放在 Model 的访问器（Accessor）中

**命名规则**：直接用职责名（如 `DepartmentTree`、`DataScopeResolver`），无需强制加 `Service` 后缀。

### 2.4 包 composer.json 规范

Library 包的 `composer.json` 与 Skeleton 项目（`"type": "project"`）有本质区别，以下为目标结构：

```json
{
    "name": "laravelstack/filament-admin",
    "type": "library",
    "description": "Laravel + Filament 后台基础 Library 包",
    "license": "MIT",
    "require": {
        "php": "^8.3",
        "laravel/framework": "^13.0",
        "filament/filament": "^5.0",
        "spatie/laravel-permission": "^6.0",
        "bezhansalleh/filament-shield": "^4.0",
        "spatie/laravel-activitylog": "^4.0",
        "stephenjude/filament-two-factor-authentication": "^4.0",
        "solution-forest/filament-tree": "^4.0",
        "alizharb/filament-activity-log": "^1.3"
    },
    "require-dev": {
        "pestphp/pest": "^4.0",
        "pestphp/pest-plugin-laravel": "^4.0",
        "larastan/larastan": "^3.0",
        "laravel/pint": "^1.0",
        "orchestra/testbench": "^10.0"
    },
    "autoload": {
        "psr-4": {
            "FilamentAdmin\\": "src/"
        }
    },
    "autoload-dev": {
        "psr-4": {
            "FilamentAdmin\\Tests\\": "tests/"
        }
    },
    "extra": {
        "laravel": {
            "providers": [
                "FilamentAdmin\\FilamentAdminServiceProvider"
            ]
        }
    }
}
```

**关键说明：**

1. `"type": "library"`：必须声明，区别于 `"project"` 类型的 Skeleton；Packagist 依此区分包类型。
2. `"extra.laravel.providers"`：声明 ServiceProvider，Laravel 的 Package Auto-Discovery 机制将自动注册，用户无需手动修改 `bootstrap/providers.php`。
3. `"autoload.psr-4"`：命名空间 `FilamentAdmin\` 映射到 `src/` 目录，所有包源码放此处。
4. **`require-dev` 用 `orchestra/testbench`**：Library 包测试依赖 Testbench（模拟 Laravel 环境），而不是完整的 Laravel 应用。当前 Skeleton 阶段用的是真实 Laravel 应用 + `filamentadmin_test` 数据库，重构到 `src/` 后改为 Testbench。
5. **不应包含**：`"repositories"`（本地 path 仓库）、`"scripts.dev"`（启动脚本）等仅适用于 Skeleton 项目的字段。

> **现状说明**：当前仓库的 `composer.json` 仍是 `"type": "project"` 的 Skeleton，将在重构阶段按以上规范替换。

## 3. 代码规范

### 3.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 类名 | PascalCase | `AdminUserResource`, `LoginLogPolicy` |
| 方法名 | camelCase | `getEloquentQuery()`, `canEditPassword()` |
| 变量名 | camelCase | `$adminUser`, `$loginLogs` |
| 常量名 | UPPER_SNAKE_CASE | `SUPER_ADMIN_ROLE`, `MAX_LOGIN_ATTEMPTS` |
| 数据库表名 | snake_case (复数) | `admin_users`, `login_logs` |
| 数据库字段名 | snake_case | `created_at`, `is_active` |
| 路由/URL | kebab-case | `/admin/login-logs` |

### 3.2 注释规范

- **PHPDoc**：所有公共方法、类属性必须包含 PHPDoc 注释。
- **语言**：注释内容使用**简体中文**。
- **示例**：
  ```php
  /**
   * 获取管理员列表查询构建器
   *
   * @return Builder<AdminUser>
   */
  public static function getEloquentQuery(): Builder
  {
      // ...
  }
  ```

### 3.3 代码质量工具

| 工具 | 用途 | 配置 |
|------|------|------|
| **Laravel Pint** | 代码风格格式化 | `pint.json` (遵循 PSR-12) |
| **Larastan (PHPStan)** | 静态分析，检查潜在错误 | `phpstan.neon` (Level 6) |
| **Pest** | 测试框架 | `phpunit.xml` |

**CI 卡点**：
- PR 合并前必须通过 `composer pint:test` (风格检查)。
- PR 合并前必须通过 `composer phpstan` (静态分析)。
- PR 合并前必须通过 `composer test` (测试用例)。

### 3.4 测试规范

#### 测试描述语言

Pest 测试使用**中文** `it()` 描述，直接表达业务语义：

```php
it('超级管理员绕过所有权限检查', function () {
    // ...
});

it('普通管理员无法访问其他部门的数据', function () {
    // ...
});
```

#### Feature vs Unit 划分

| 测试类型 | 路径 | 测试内容 |
|---------|------|---------|
| Feature | `tests/Feature/` | Filament Resource 页面渲染、Artisan 命令、集成流程 |
| Unit | `tests/Unit/` | 纯逻辑（Service 方法、Model Accessor、Policy 规则） |

#### 认证 Guard

涉及管理员认证的测试，必须显式传入 `admin` guard：

```php
$this->actingAs($adminUser, 'admin');
```

#### 权限缓存清理

使用 `spatie/laravel-permission` 的测试，每个套件开始前需清理缓存，避免跨测试污染：

```php
use Spatie\Permission\PermissionRegistrar;

beforeEach(function () {
    app(PermissionRegistrar::class)->forgetCachedPermissions();
});
```

#### 当前与目标的差异

| 阶段 | 测试基础 | 数据库 |
|------|---------|-------|
| 当前（Skeleton） | 完整 Laravel 应用 + `RefreshDatabase` | `filamentadmin_test`（MySQL） |
| 迁移阶段一（Library 骨架 + 代码迁移） | 仍使用完整 Laravel 应用 + MySQL | `filamentadmin_test`（MySQL，不变） |
| 迁移阶段二（独立发布准备） | `orchestra/testbench` | 内存 SQLite 或可配置 |

> **说明**：代码从 `app/` 迁移到 `src/` 时，测试框架**暂不切换** testbench，保持 MySQL 以确保迁移过程中测试仍能完整运行。testbench 切换是独立的后续步骤，待包基本稳定后单独推进。

## 4. 开发流程规范

### 4.1 分支管理

- **main**：主分支，随时可发布状态。
- **feature/xxx**：功能分支，从 main 切出，开发完成后合并回 main。
- **release/vX.Y.Z**：发布分支，用于发布前的最终测试和修复。

### 4.2 提交规范

Commit Message 格式：`<type>: <description>`

| type | 描述 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 Bug |
| `docs` | 文档更新 |
| `style` | 代码格式调整（不影响逻辑） |
| `refactor` | 重构（既不是新功能也不是修复） |
| `test` | 测试相关 |
| `chore` | 构建过程或辅助工具的变动 |

**示例**：
- `feat: 添加管理员登录日志功能`
- `fix: 修复角色权限分配失败的问题`
- `docs: 更新安装指南`

## 5. 安全规范

### 5.1 包内敏感信息处理

作为 Library 包，对敏感信息的处理不同于 Skeleton 应用：

- **禁止**在包源码（`src/`）中硬编码任何密码、Secret、API Key。
- **禁止**在包的默认配置文件（`config/filament-admin.php`）中包含高安全风险的默认值（如弱密码、公开密钥）。
- 包内代码读取配置必须通过 `config('filament-admin.xxx')`，**禁止**在 `src/` 内直接调用 `env()`（`config/filament-admin.php` 文件本身除外）。
- 包发布的示例配置中，敏感项必须使用占位符或空字符串，并注释说明如何通过 `.env` 覆盖。

> 关于用户项目的 `.env` 和 `.gitignore` 管理，是用户项目自身的职责，包文档（`wiki/`）中应说明，但不属于包代码规范。

### 5.2 权限控制

- 所有后台路由必须经过 `auth:admin` 中间件。
- 所有 Resource 操作必须配置对应的 Policy。
- 超级管理员通过 `Gate::before()` 绕过检查，但普通管理员必须严格校验。

### 5.3 数据校验

- 所有用户输入必须使用 Laravel Validator 或 Form Request 进行校验。
- 敏感操作（如删除、修改密码）建议增加二次确认或密码验证。
