# FilamentAdmin 项目开发规划

> 更新时间：2026-05-29  
> 文档定位：整体开发规划说明。本文用于指导后续开发节奏，不作为对外宣传稿，也不作为代码完成状态清单。  
> 核心原则：按功能块分期推进，做成一块、发布一块。每一期都必须形成可以真实使用、可以演示、可以维护的后台能力。

---

## 一、规划原则

FilamentAdmin 后续不再按“大版本一次性堆功能”的方式推进，而是按一期、二期、三期这样的功能块节奏交付。每一期都是一个相对完整的后台能力，做完后可以单独发布、单独演示、单独写文档。

这套节奏的重点是：

- 每一期只围绕一个明确主题，不同时铺开一堆半成品。
- 每一期都要有后台入口，不能只停留在模型、迁移或底层包接入。
- 每一期都要补齐权限、测试、文档和阶段说明。
- 一个功能没有形成完整闭环，就不进入下一期。
- 如果某一期范围过大，就继续拆成更小的“期”，不要硬塞。

## 二、分期总览

| 期次 | 功能块 | 核心目标 |
|------|--------|----------|
| 一期 | 后台基础管理完整包 | 管理员管理、管理员日志、角色与权限、菜单规则、部门组织、数据权限、操作日志审计 |
| 二期 | 插件架构与插件中心 | 建立本地插件识别、启停、配置入口和依赖检查能力 |
| 三期 | 项目上线 | 补齐首页体验、文档、CI、发布说明和安装体验 |
| 四期 | 配置自动上线和整套流程|
| 五期 | 远程插件市场索引 | 提供插件发现、搜索、详情和安装指引 |
| 六期 | 探讨目录优化可能， 是否可以改成， laravel+filament+filamentadmin|
| 六期 | 系统配置 | 建立配置中心，承载站点配置、上传配置、安全配置、日志配置和插件配置入口 |
| 七期 | 媒体库 | 统一文件上传、预览、管理和复用，为头像、Logo、附件打基础 |
| 八期 | 基础导出 | 为后台表格提供安全可控的数据导出能力 |
| 九期 | API 基础规范 | 定义认证、响应格式、错误码和 API 文档规范 |
| 十期 | CRUD 开发规范 | 沉淀后续业务模块开发模板，避免每个模块重新摸索 |

## 三、一期：后台基础管理完整包

一期优先做后台自身管理能力。这个功能块可以理解为传统后台里的“常规管理 / 权限管理”区域，不是单个页面，而是一组相互关联的后台治理基础能力。

一期包含七块：管理员管理、管理员日志、角色与权限、菜单规则、部门组织、数据权限、操作日志审计。

详细设计见 `docs/superpowers/specs/2026-05-29-phase-1-admin-foundation-design.md`，实施计划见 `docs/superpowers/plans/2026-05-29-phase-1-admin-foundation.md`。

### 管理员管理

管理员管理负责后台账号的完整生命周期。

需要覆盖：

- 管理员列表：展示用户名、邮箱、状态、角色、2FA 状态、创建时间、最后登录信息。
- 管理员创建和编辑：支持基础资料、密码、状态、角色分配。
- 管理员禁用：禁用后不能登录，并且要有测试覆盖。
- 软删除和恢复：后台提供删除、恢复能力。
- 密码重置：管理员可以为其他管理员重置密码，操作受权限控制。
- 权限接入：列表、创建、编辑、删除、恢复、密码重置都要有权限点。
- 文档说明：明确后台管理员使用 `admin` guard 和 `admin_users` 表，不使用 Laravel 默认 `users` 表。

完成标准：后台可以完整管理管理员账号，普通角色只能做自己有权限的操作。

### 管理员日志

管理员日志用于追踪后台登录行为，帮助定位登录失败、异常 IP、账号安全问题。

需要覆盖：

- 登录日志列表：展示管理员、登录账号、IP、User-Agent、登录结果、失败原因、时间。
- 日志详情：能查看完整 UA、请求上下文和失败原因。
- 筛选和搜索：按管理员、登录结果、IP、时间范围筛选。
- 只读权限：日志默认只读，不提供普通删除入口。
- 清理策略：配合系统配置，支持保留天数和清理命令。

完成标准：管理员能在后台追踪登录成功、失败和异常登录情况。

### 角色与权限

角色与权限负责后台访问控制，也是管理员管理和菜单规则的基础。

需要覆盖：

- 角色管理：使用 Shield 自带 RoleResource，不为每个 Resource 自写 RoleResource。
- 权限分组：按功能块展示权限，例如管理员管理、管理员日志、菜单规则、系统配置。
- 管理员分配角色：在管理员管理中能看到和修改管理员所属角色。
- 权限点规范：每个 Resource 的 view、create、update、delete、restore、export 等权限命名要统一。
- 超级管理员：继续使用 `super_admin` + `Gate::before()`，但不能绕过登录状态和禁用状态。
- 权限测试：覆盖超级管理员、普通角色、无权限用户、多角色合并权限。

完成标准：角色能配置权限，管理员能绑定角色，不同角色访问后台功能时能看到真实差异。

### 菜单规则

菜单规则负责后台导航和权限显示，让后台不再完全依赖代码写死菜单。

需要覆盖：

- 菜单树：支持父子级、排序、图标、路由、显示/隐藏。
- 菜单权限：菜单可以绑定权限点，没有权限时不显示。
- 导航生成：后台导航能从菜单规则生成。
- 菜单分组：支持类似“常规管理”“权限管理”这样的后台分组。
- 插件菜单预留：后续插件启用时可以注册自己的菜单，禁用时菜单消失。
- 缓存刷新：菜单变更后能刷新后台导航，不长期读旧数据。

完成标准：不同角色登录后台时，看到的菜单和能访问的功能保持一致。

### 部门组织

部门组织用于支撑数据权限，不做复杂 HR 系统。

需要覆盖：

- 部门树：支持父子级、名称、编码、排序、启用状态。
- 部门负责人：可选绑定管理员作为负责人。
- 管理员主部门：管理员账号可绑定一个主部门。
- 部门禁用：禁用部门不再作为新管理员可选部门，但不影响历史数据。
- 下级部门计算：提供本部门及下级部门 ID 的计算能力，供数据权限使用。

完成标准：后台能维护部门树，并能把管理员绑定到部门。

### 数据权限

数据权限用于控制角色能查看哪些范围的数据。

需要覆盖：

- 数据范围：全部数据、本部门数据、本部门及下级、仅本人、指定部门。
- 角色数据范围：为角色配置数据权限，不侵入 Shield 自带 RoleResource。
- 多角色合并：多个角色的数据范围按允许范围合并；任一角色拥有全部数据则视为全部数据。
- 超级管理员：不受数据权限限制，但不能绕过账号禁用和软删除。
- 实际接入：一期至少接入管理员列表和登录日志列表，并沉淀可复用服务。

完成标准：不同角色查看管理员和登录日志时，数据范围符合配置。

### 操作日志审计

操作日志用于记录关键后台行为，解决“谁在什么时候做了什么”的问题。

需要覆盖：

- 操作日志接入：管理员、角色、菜单、部门、数据权限等关键操作先接入。
- 日志列表和详情：展示操作人、动作、对象、时间、IP、变更内容。
- 变更 diff：当前先做简单 JSON 展示，后续再优化视觉。
- 筛选能力：按操作人、对象类型、动作、时间范围筛选。
- 清理策略：支持按保留天数清理普通操作日志。

完成标准：关键后台操作可追溯，出现误操作时能查到是谁、什么时候、改了什么。

一期整体完成后，后台应该能管理管理员、分配角色和权限、查看管理员登录日志、维护菜单规则、维护部门、控制数据范围、追踪关键操作。这是后续所有功能继续往下开发的基础。

## 四、二期：插件架构与插件中心

二期开始进入插件能力。插件中心不能在基础能力不完整时硬做，它需要依赖菜单、配置、权限、日志和文档规范。

需要覆盖：

- 插件类型：工具型 package 留在 `vendor/`，业务型 module 解包到 `Modules/`。
- 插件元数据：名称、版本、类型、说明、作者、兼容版本、配置入口。
- 生命周期语义：安装、启用、禁用、卸载、升级分别是什么意思。
- 插件扫描：扫描 Composer 包和 `Modules/`，写入插件表。
- 插件中心：展示已安装插件、版本、状态、说明、配置入口。
- 启用禁用：启用后注册后台能力，禁用后隐藏菜单、Resource 和配置入口。
- 依赖检查：禁用被依赖插件时给出提示，当前先做基础依赖。

完成标准：后台能管理本地已安装插件，插件启停能真实影响后台能力。

## 五、三期：项目上线

三期做项目上线收口。这里不是简单美化，而是让项目具备对外展示、安装和维护的完整体验。

需要覆盖：

- 仪表盘统计：管理员数、登录次数、插件数、系统状态等真实指标。
- 快捷入口：管理员管理、角色与权限、系统配置、插件中心、文档入口。
- 系统信息：PHP、Laravel、Filament、数据库、缓存、队列状态。
- 后台体验：Logo、主题色、侧边栏、表格信息密度。
- README：项目定位、特性、安装、截图、文档入口。
- 安装文档：环境要求、数据库、迁移、创建管理员、本地域名。
- CI 和质量门槛：test、phpstan、pint、composer audit。
- Release：CHANGELOG、UPGRADE、Tag、Packagist、Release Notes。

完成标准：项目具备阶段性公开发布条件，新用户能按文档安装并理解当前已经完成的能力。

## 六、四期：远程插件市场索引

四期做远程插件市场索引。这个阶段先解决“发现插件”和“知道怎么安装”，不做在线购买、后台自动安装和 License 校验。

需要覆盖：

- 远程索引格式：JSON 包含名称、版本、分类、兼容性、安装命令、文档链接。
- 市场浏览：分类、搜索、详情页、版本信息。
- 安装指引：package 显示 Composer 命令，module 显示下载和解包说明。
- 来源标签：官方、推荐、社区。
- 品质信息：测试状态、文档状态、兼容版本、最近更新。
- 商业化预留：保留 paid、license_required、vendor_id 等字段，但不实现付款。

完成标准：后台能浏览远程插件，用户能复制安装命令，并理解插件来源和兼容性。

## 七、五期：系统配置

五期建立配置中心。它不只是一个“站点名称”页面，而是后续上传、日志、安全、插件能力的统一配置入口。

需要覆盖：

- 基础配置：站点名称、后台标题、Logo、备案信息、联系方式。
- 上传配置：文件大小、允许类型、默认磁盘、图片尺寸策略。
- 安全配置：登录限制、2FA 提示、账号安全开关。
- 日志配置：登录日志和操作日志的保留天数。
- 插件配置入口：插件可以声明自己的 Settings 类，并出现在配置中心。
- 配置缓存：配置变更后缓存能正确失效。

完成标准：后台能修改常用系统配置，业务代码和插件能稳定读取配置。

## 八、六期：媒体库

六期建立统一媒体库，为头像、Logo、富文本图片、附件上传和后续云存储插件打基础。

需要覆盖：

- MediaLibrary 接入：优先使用 Spatie MediaLibrary 和 Filament 官方/社区插件。
- 媒体管理页面：文件列表、预览、下载、删除、筛选。
- Collection 规范：例如 avatar、logo、attachments、content_images。
- 上传安全：文件大小、MIME、扩展名、危险文件拦截。
- 实际场景接入：至少接入管理员头像和系统 Logo，避免媒体库孤立存在。

完成标准：后台能上传、预览、管理文件，并能被真实功能使用。

## 九、七期：基础导出

七期补齐后台高频的数据导出能力。导出不能只是一个按钮，还要考虑权限、字段安全和审计。

需要覆盖：

- 表格导出：核心 Resource 支持导出当前筛选结果。
- 字段控制：默认不导出密码、Token、密钥等敏感字段。
- 导出权限：导出动作单独有权限点。
- 导出日志：记录谁在什么时候导出了什么。
- 开发规范：说明新 Resource 如何接入导出。

完成标准：管理员能安全导出数据，导出行为可追溯。

## 十、八期：API 基础规范

八期定义 API 基础规则。这里不追求大而全，重点是让后续插件和业务模块不要各写各的响应格式。

需要覆盖：

- API 认证：Token 登录、退出、受保护路由。
- API 路由分组：统一 API 前缀和中间件，是否使用 `/api/v1` 版本号按实际需要确定。
- 统一响应：成功、失败、验证错误、分页响应格式一致。
- 业务异常：提供 BusinessException 和错误码机制。
- 错误码文档：核心错误码有固定范围，插件可注册自己的错误码。
- API 文档：先写静态规范，自动生成等 API 稳定后再做。

完成标准：API 的认证、响应、错误处理和文档格式稳定。

## 十一、九期：CRUD 开发规范

九期沉淀开发规范。这不是给最终用户看的功能，而是给后续开发者和插件作者用的标准模板。

需要覆盖：

- Resource 规范：表单、表格、筛选、Action、Infolist、RelationManager 怎么组织。
- Model 规范：命名、软删除、Factory、Seeder、Casts、PHPDoc。
- Policy 规范：CRUD 权限、软删除权限、超级管理员逻辑。
- 测试规范：中文 Pest 描述、权限边界、数据库断言、事件测试。
- 文档模板：每个功能完成时应该补哪些文档。
- 示例业务模块：做一个小而完整的 CRUD 样例，作为后续复制模板。

完成标准：新开发者能照着规范完成一个标准业务模块，而不是到处猜项目习惯。

## 十二、每期交付门槛

每一期完成前，都必须过一遍交付门槛。

- 后台可用：功能有真实入口，管理员能在后台完成对应操作。
- 权限可控：功能接入 `admin` guard、角色权限和必要的 Policy。
- 数据可靠：迁移、模型、Factory、Seeder 或默认数据齐全。
- 行为可查：涉及安全、配置、删除、权限变更的操作要接入日志。
- 测试覆盖：至少覆盖成功路径、失败路径、权限边界和关键数据断言。
- 文档同步：更新功能文档、开发规范或公开说明，不让文档落后于代码。
- 质量检查：完成前跑 `composer test`、`composer phpstan`、`composer pint:test`；无法运行时记录原因。

## 十三、暂不进入近期主线的范围

这些能力重要，但暂不进入近期功能块主线，避免再次把功能拆散：

- 插件异步安装和在线升级：涉及队列、进程重载和部署环境差异，等插件中心稳定后再排期。
- 插件商业化闭环：涉及开发者入驻、支付、授权、私有源和合规文档，等插件市场基础跑通后再排期。
- 通知系统：站内、邮件、短信、Webhook 适合统一设计，等后台基础能力稳定后再排期。
- 定时任务和队列可视化：近期只保留命令和 Scheduler 基础。
- API 文档自动生成：先保证 API 规范稳定。
- 完整多语言后台：近期只保留语言包和文案规范。
- 高级安全策略：IP 白名单、异地登录、二次确认等先预留。

## 十四、文档维护规则

- `docs/guide/overview.md`：面向公开发布的项目概览，只写目标和真实完成状态，不虚标。
- `doc/一期开发后的梳理.md`：记录当前代码状态、差距和阶段复盘。
- `doc/项目开发规划.md`：记录分期开发路线、每期功能范围和交付门槛。
- `docs/features/*.md`：每一期完成前必须补齐对应使用说明。
- `docs/development/*.md`：沉淀 CRUD、插件、权限、测试等开发规范。
- `docs/superpowers/specs/*.md`：保留详细规格和历史计划，做具体功能设计时再引用。

本文的作用是约束后续节奏：不要为了看起来进展很多，把每个功能都只做一点点。宁愿慢一点，也要每期交付一个真正成型的后台能力。
