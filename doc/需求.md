# FilamentAdmin

## 项目定位

**Laravel + Filament 后台基础平台，主打两大特色：开箱即用的代码市场，与组合最优的代码基座。**

每次新项目不再重复搭后台基础设施。基于 Filament 5，预装配权限、系统配置、媒体库、操作日志等通用能力，并通过双轨制插件市场支持工具扩展与业务模块二开。MIT 协议，免费商用。

### 两大特色

**特色一：开箱即用的代码市场**

对标 FastAdmin 多年沉淀的"应用插件市场"——用户在后台搜索"商城""官网""CMS"，下载即用，需要二开的代码直接落到自己项目里。FilamentAdmin 用双轨制方案实现：
- **工具型插件**（OSS、短信、支付、Excel 处理等）→ 住 `vendor/`，标准 Composer 包，配置即用
- **业务模块型插件**（商城、官网、论坛、知识付费等）→ 解包到 `Modules/`，代码归项目所有，可自由二开

第一版做本地插件中心 + 远程索引浏览 + 安装引导 + 商业化预留；第二版补齐异步安装、在线升级、ZIP 离线安装，并**正式启动商业化闭环**（付费插件、开发者入驻、平台分成）。

**特色二：组合最优的代码基座**

不重复造轮子，把市面上最被验证过的 Laravel / Filament 扩展包按"开箱即用"的标准组合起来，并提供清晰的定制层与扩展点说明。开发者拿到项目后，看一份文档就能知道"用了哪些包、为什么选这些、做了哪些定制、二开时应该在哪一层下手"。详细包清单与选型理由见后文"技术选型与版本规范"和"代码基座默认集成清单"。

> **与 FastAdmin 的关系说明**：FastAdmin 的两大核心特色——开箱即用的后台体验 + 代码插件市场——正是本项目要对标的目标。技术栈换成 Laravel + Filament 是为了享受 Laravel 生态红利，但产品形态、用户预期、市场定位都直接对标 FastAdmin。代码生成 CRUD 这种能力 Filament 自带（`make:filament-resource`），不构成差异点。

## 需求：

希望沉淀一套对标 FastAdmin 的 Laravel + Filament 后台基础平台。专注提供后台系统的通用底座、权限体系、插件机制、快速开发规范和基础运维能力。

具体需求如下：

本项目主打开源生态，文档体系必须完备：安装记录、变更记录、定制说明都要清晰可查。核心是消除二次开发者的使用顾虑——让任何拿到本项目的开发者都能快速识别"框架在 Laravel / Filament 默认行为基础上做了哪些定制"，避免因不可知改动产生顾虑而放弃使用。

- 后台能力要像 FastAdmin 一样开箱即用，但技术栈换成 Laravel + Filament，尽量复用 Laravel 生态和 Filament 扩展机制。这一点非常重要。
- 作为后续所有业务项目的后台开发底座，优先解决"快速搭后台、快速接业务、快速扩展插件"的问题。
- 默认安装后就具备后台登录、管理员、角色权限、菜单、系统配置、操作日志、附件上传、插件中心等通用能力。
- 支持开发者通过 Laravel Model、Migration、Seeder、Policy、Filament Resource 快速新增业务模块。
- 支持多角色协作，至少满足超级管理员、管理员、运营、编辑、审核等角色的权限分配基础。
- 插件市场是 FilamentAdmin 的长期核心能力之一，用于沉淀行业模块、运营模块、主题模块、集成模块和业务扩展模块，让后续项目可以通过安装插件快速获得能力。
- 插件市场第一阶段不追求完整商业化闭环，先实现本地插件中心、插件启停、插件配置、插件依赖、版本信息和安装说明，后续再扩展远程市场、审核、付费、升级和分发机制。


## 对标 FastAdmin 默认能力：

FastAdmin 默认安装后，本质上是一套"后台快速开发框架"，核心不是官网 CMS，而是后台底座和扩展生态。本项目应优先对标这些能力。

- 权限管理：管理员、角色/分组、菜单规则、权限节点、按钮权限、数据权限思路。
- 后台菜单：后台导航、菜单规则、权限绑定、控制器/页面入口管理。
- CRUD 快速开发：复用 Filament 官方 Artisan 命令（`filament:make-resource` 等）生成 CRUD 骨架，配合本项目沉淀的规范模板（基类、Trait、Policy 约定）让开发者按规范快速新增业务模块。
- 插件中心：插件安装、卸载、启用、禁用、升级、配置和扩展入口。
- 附件上传：图片、文件上传，默认本地存储，云存储能力以插件形式扩展（OSS、S3 等）。
- 会员/API 基础：FastAdmin 有通用会员模块和 API 模块；本项目只做后台权限模块、后台管理员模块，不做前台通用会员和 API 模块。
- 多语言：FastAdmin 支持多语言；FilamentAdmin 第一版先不做复杂多语言，只预留语言包和后台文案扩展方式。
- 操作体验：后台表格、筛选、排序、批量操作、导入导出、软删除/回收站、状态切换等通用管理体验。
- 开发辅助：命令行工具、静态资源发布、插件资源发布等开发效率能力；API 文档生成暂不纳入第一版。


## 具体功能：

- 后台登录与账号管理：支持后台登录、退出、修改密码、管理员账号创建、禁用和基础资料维护。
- 角色与权限管理：支持角色划分、权限分配、菜单可见范围控制、操作权限控制，后续可扩展数据权限。
- 后台菜单管理：支持后台菜单、分组、图标、排序、权限绑定和插件菜单接入。
- 系统配置管理：支持站点级基础配置、上传配置、邮件配置、短信配置、插件配置等统一配置入口；配置按模块分组，支持文本、开关、下拉、图片等多种配置类型；配置结果缓存，避免每次请求查库。
- 操作日志与登录日志：操作日志与登录日志分表存储；操作日志自动记录 Model 变更前后 diff；支持按天数上限定期自动清理日志，上限和定期清理同步配置。
- 附件与文件管理：支持图片、视频、附件等资源上传、分类、搜索、复用，第一版先做后台通用附件能力，默认本地存储。
- 通用 CRUD 规范：沉淀 Laravel Model、Migration、Seeder、Policy、Filament Resource、Form、Table、Action、Filter、Infolist、Widget 的组织规范，让后续业务模块可以快速复制。
- 软删除与回收站：为常见后台资源提供软删除、恢复、彻底删除等通用管理能力。
- 数据导入导出：第一版可以先支持基础 Excel/CSV 导出，导入能力按业务模块逐步接入。
- API 基础能力：提供统一 API 返回结构、鉴权边界、错误格式和资源输出规范，方便项目二、项目三读取数据；后台 API 路由与业务 API 路由分离，统一加 `/api/v1` 版本前缀。
- 插件中心管理：支持在后台查看已安装插件、插件状态、插件版本、插件说明、依赖要求、配置入口和启停状态。
- 插件安装与启停：支持通过 Composer 包或本地插件目录安装插件，后台可以启用、停用和查看插件运行状态。
- 插件配置管理：支持插件声明自己的配置项，并在 Filament 后台生成对应配置页面，避免每个插件都重复开发设置页。
- 插件菜单与权限接入：支持插件向后台注册菜单、页面、资源、权限点和操作入口，并能接入统一角色权限体系。
- 插件数据迁移与初始化：支持插件携带 Migration、Seeder、配置发布和资源发布能力，安装后可以完成必要的数据表和初始数据准备。
- 插件市场索引：第一阶段先支持读取本地或远程 JSON 索引，展示插件名称、分类、版本、作者、说明、兼容版本、安装命令和文档链接，为后续真正的市场化分发预留空间。


## 代码基座价值主张

本项目第二大特色是"组合最优的代码基座"。这不是技术包装，而是给二次开发者的具体承诺：

**承诺一：透明可审计**
- 没有黑盒。所有定制都在 `architecture/customizations.md` 列出：改了哪个包的什么行为、为什么改、改在哪个文件、如何还原默认行为
- `composer.json` 里每一个非标准依赖都能在文档里查到"为什么选它、和哪些替代方案对比过"

**承诺二：组合最优而非碰运气**
市面上有大量"Laravel + Filament 启动模板"是作者随手攒的轮子组合，遇到坑没人维护。本项目对每个核心扩展点的选型遵循以下标准：

| 选型维度 | 硬性要求 |
|---------|---------|
| 下载量 | Packagist 累计下载量 ≥ 100 万（核心依赖 ≥ 1000 万）|
| 维护活跃度 | 近 6 个月有 commit，issue 平均响应 ≤ 30 天 |
| 文档完整度 | 官方 README 含完整安装/配置/进阶用法说明 |
| 生态兼容性 | 与 Filament 官方插件无已知冲突 |
| 团队背书 | 来自 Spatie / Filament 官方 / Laravel 官方 / 著名社区维护者优先 |

不满足上述标准的方案不进入本项目主体集成，可作为可选插件。

**承诺三：升级有路径**
- 每个集成包都锁定主版本，patch/minor 自由升级
- 集成包发布大版本时，本项目在下一个主版本中跟进升级，升级前在 GitHub Issues 公开"升级评估报告"
- 任何依赖的"破坏性变更"都在 `UPGRADE.md` 中明确给出迁移代码示例

**承诺四：能挖洞，也能填洞**
- 集成包暴露的所有扩展点（Trait / Contract / Event）在 `docs/development/base-classes.md` 集中说明
- 业务方如需替换某个集成包（如不用 Spatie 改用 Bouncer），文档提供"替换路径"章节，至少说明替换工作量级别（小时 / 天 / 周）

- 队列监控（`laravel/horizon`）：仅 Redis 队列项目需要

> 一句话总结：主包只装"任何后台项目都必装"的东西，能让人犹豫一秒钟的依赖一律放进可选插件。这是"开箱即用"和"主包不臃肿"的平衡点。


## 实现方案 / 落地清单：

> 实施总原则：通用能力优先复用 Laravel / Filament 社区成熟方案，不重复造轮子；只有现有方案无法覆盖时才自研。本节为整体落地节奏，技术选型细节见后文"技术选型与版本规范"。

1. 第一步，使用 Laravel + Filament 创建 FilamentAdmin。Laravel 负责后台业务、数据模型、接口、权限、队列和邮件等服务端能力，Filament 负责快速搭建后台管理界面。
2. 第二步，先把 FilamentAdmin 定位成"后台基础平台"，不急着做官网、内容、运营这些业务模块，优先沉淀后台开发框架能力。
3. 第三步，补齐后台通用能力，包括后台登录、管理员、角色权限、菜单、系统配置、操作日志、附件上传、软删除、基础导入导出和统一 API 规范。
4. 第四步，沉淀通用 CRUD 开发规范，包括 Model、Migration、Seeder、Policy、Filament Resource、Form、Table、Action、Filter、Infolist、Widget 的组织方式。
5. 第五步，设计插件机制和插件中心。插件底层优先复用 Laravel Composer 包、Service Provider、Package Auto-Discovery、Migration、Config Publish 这些成熟机制；后台侧复用 Filament Plugin、Panel、Resource、Page、Widget 这些扩展点，不重新发明一套封闭插件系统。
6. 第六步，先实现插件中心 MVP，包括已安装插件列表、插件启停状态、插件配置入口、插件依赖说明、本地插件索引和远程插件索引读取。第一版不急着做在线购买、自动支付、复杂审核和完整云端分发。
7. 第七步，再补轻量定时任务、事件联动、队列任务和通知能力，让这套底座具备基础自动化能力，但先不在这一层把重队列和重异步系统做得太复杂。
8. 第八步，把这套项目整理成真正可以复制和复用的后台基础平台，作为项目二、项目三以及后续业务项目的共同起点。
9. 至此，本项目完成。


## FilamentAdmin 插件市场设计：

插件市场不是从零造一个和 Laravel 生态割裂的系统，而是站在 Laravel 和 Filament 的成熟扩展机制上做产品化封装。

### 双轨制插件架构

FilamentAdmin 的插件分为两种完全不同的性质，必须用两套不同的机制承载：

| 类型 | 典型例子 | 安装位置 | 二开需求 | 更新方式 |
|------|---------|---------|---------|---------|
| **工具型插件** | 阿里云 OSS、短信、支付宝 | `vendor/` via Composer | 不需要改代码 | `composer update` 自动 |
| **业务模块型插件** | 商城、官网、论坛、知识付费 | `Modules/` via nwidart | **买来就要二开** | 手动 merge，代码归买家 |

**为什么需要两套**：

工具型插件装完配置就用，不需要碰代码，住在 `vendor/` 和 Laravel 框架本身住在 `vendor/` 是一个道理。

业务模块型插件不同——有人开发了一套商城，在市场出售，买家买了之后大概率要改模板、加字段、改业务逻辑，这些改动需要提交到买家自己的 Git 仓库里长期维护。如果代码在 `vendor/`，买家无法编辑，`composer update` 还会覆盖修改，这条路走不通。业务模块型插件安装后代码必须解包到项目目录里，成为买家自己的代码。

**安装后的目录结构**：

```
your-project/
├── Modules/                        ← 业务模块型插件的家（nwidart/laravel-modules）
│   ├── Mall/                       ← 买来的商城模块，现在是你的代码，随便改
│   │   ├── app/
│   │   │   ├── Models/
│   │   │   ├── Http/
│   │   │   └── Filament/Resources/
│   │   ├── database/migrations/
│   │   ├── resources/
│   │   └── module.json
│   └── Website/                    ← 买来的官网模块，同样是你的代码
├── vendor/                         ← 工具型插件，不需要改的那些
│   └── author/oss-plugin/
└── app/                            ← 自己写的其他业务代码
```

**底层技术**：业务模块型插件基于 `nwidart/laravel-modules`（1553 万次下载，6.1k stars，Laravel 模块化事实标准）。

### 架构边界认知

PHP-FPM 进程模型下，ServiceProvider 在进程启动时一次性确定，运行时无法真正热插拔。FilamentAdmin 对两种类型分别处理：

- **工具型插件启停**：插件的 Composer ServiceProvider 始终通过 Laravel Package Auto-Discovery 注册（无法跳过，也没必要跳过），启停发生在 **Filament Panel 层**——AdminPanelProvider 在 `panel()` 链上根据数据库中插件的启用状态决定是否调用 `->plugin(XxxPlugin::make())`。禁用的插件不会出现在后台菜单、Resource 列表、配置入口中，对应的路由和权限也不会注册，对最终用户等价于"未安装"。后台切换启停状态后下次请求生效。
- **业务模块型启停**：`nwidart/laravel-modules` 通过 `modules_statuses.json` 控制模块是否加载，效果等价。

> 这种"Panel 层禁用"方案放弃了"完全卸载 ServiceProvider"的幻想，但换来了简单可靠、不依赖框架启动顺序、不会因为禁用插件破坏 Composer 依赖图的稳定性。这是 Filament 生态目前事实上的处理方式。

#### 启停、安装、卸载的语义区分（重要）

这三个操作的边界必须在文档中说清楚，避免用户混淆"为什么禁用了插件 `php artisan` 还能跑它的命令"。

| 操作 | 触发场景 | 是否需要重启进程 | 实际效果 |
|------|---------|----------------|---------|
| **启用 / 禁用** | 用户在后台一键切换 | ❌ **不需要**，下一个请求生效 | 后台菜单/路由/权限/Action/配置入口消失或显现；插件 ServiceProvider 注册的命令、配置文件、Migration 候选**仍然存在** |
| **安装** | 第一版：用户在终端执行 `composer require`；第二版：后台一键触发异步队列 | ✅ **需要**重启/reload PHP 进程（Composer Auto-Discovery 在框架启动期生效）| 插件代码进入 `vendor/`，下次请求起完整可用 |
| **卸载** | 用户在终端执行 `composer remove`，或第二版后台一键 | ✅ **需要**重启/reload PHP 进程 | 插件代码从 `vendor/` 移除，相关 Composer 依赖一并清理 |

**为什么"启停不需要重启"很重要**：
- 线上插件出问题时，运维可以**秒级在后台禁用插件止血**，不需要 SSH 登录服务器 reload PHP-FPM
- A/B 测试场景可以快速开关插件
- 多管理员协作时，编辑/运营角色无服务器权限也能操作启停

**"启停"的"漏出"边界（用户应当知晓）**：
禁用插件后，下列内容仍然存在于系统中（属于设计，不是 bug）：
- `php artisan` 仍能看到并执行该插件的命令（便于运维维护数据）
- 插件配置文件依然被加载（占少量内存）
- `php artisan migrate` 仍会看到该插件的 Migration（防止数据回滚意外）

如果用户希望"彻底清除"，应执行卸载（`composer remove`）而非禁用。第一版插件中心的禁用按钮旁会提供"如何彻底卸载"的提示链接。

| 能力 | FastAdmin | FilamentAdmin 第一版 |
|------|-----------|---------------------|
| 插件列表展示 | 完整实现 | 完整实现 |
| 插件启停（后台操作） | 修改 ini，下次请求生效 | 等价实现，下次请求生效 |
| 插件配置 UI | 完整实现 | 完整实现 |
| 业务模块二开支持 | 完整实现（addons/ 目录） | 完整实现（Modules/ 目录）|
| 一键在线安装 | 完整实现 | **第一版不做**，展示安装命令 |
| 在线升级 | 完整实现 | **第一版不做**，提示升级命令 |
| 插件热插拔（不重启生效） | 完整实现 | **永远无法实现**（PHP-FPM 进程模型根本限制）|

### 插件开发标准规范

所有插件在 `composer.json` 的 `extra.filament-admin` 中声明类型，FilamentAdmin 的插件中心据此决定安装行为：

```json
{
  "extra": {
    "laravel": {
      "providers": ["Vendor\\Plugin\\PluginServiceProvider"]
    },
    "filament-admin": {
      "type": "package",
      "name": "阿里云 OSS",
      "description": "插件功能说明",
      "category": "存储"
    }
  },
  "require": {
    "php": "^8.3",
    "laravel/framework": "^13.0",
    "filament/filament": "^5.0",
    "filament-admin/core": "^1.0"
  }
}
```

> 版本约束统一使用 `^主版本.0` 而不是 `^主版本.次版本`，遵循 Laravel 官方在 [Release Notes](https://laravel.com/docs/13.x/releases) 中给出的写法。锁到 minor 版本会无谓限制兼容性，且在框架打 patch 更新时拖累插件可用性。

`type` 字段取值：
- `"package"` → 工具型，住 `vendor/`，通过 Composer 管理
- `"module"` → 业务模块型，解包到 `Modules/`，代码归安装方所有

**工具型插件（`type: package`）开发规范**：
- 标准 Composer Package，通过 `spatie/laravel-package-tools` 简化 ServiceProvider
- 实现 `Filament\Contracts\Plugin` 接口（`getId` / `register` / `boot`）
- 配置项通过 `spatie/laravel-settings` 声明，自动生成 Filament 配置页
- 携带的 Migration 通过 `hasMigrations()` 声明，安装后用户手动执行

**业务模块型插件（`type: module`）开发规范**：
- 基于 `nwidart/laravel-modules` 模块结构开发
- 同样实现 `Filament\Contracts\Plugin` 接口接入后台
- **模块 ServiceProvider 必须显式注册 Filament 资源发现**：`nwidart/laravel-modules` 的目录不在 Filament Panel 的默认扫描路径，模块需要在 `boot()` 中调用 `Filament::serving(fn() => Filament::registerResources([...]))` 或在 Plugin 类的 `register()` 中调用 `$panel->discoverResources(in: module_path('Mall', 'app/Filament/Resources'), for: 'Modules\\Mall\\Filament\\Resources')`，同样适用于 `discoverPages` 和 `discoverWidgets`。FilamentAdmin 提供 `ModuleFilamentPlugin` 抽象基类封装这套样板代码，模块开发者继承即可。**这是模块型插件踩坑率最高的点，文档必须显著提示。**
- `module.json` 声明模块名称、版本、依赖、兼容的 FilamentAdmin 版本
- 分发形态：ZIP 包（市场下载）或 Composer 包（`install-path` 指向 `Modules/`）
- **更新说明必须写清楚**：代码一旦解包归买家所有，有新版本时需手动 merge，市场详情页明确提示

**所有插件通用要求**：
- 声明支持的 PHP / Laravel / Filament / FilamentAdmin 版本
- 权限点必须接入统一角色权限体系，不得绕过
- 携带的 Migration 和 Seeder 安装、升级、回滚必须有记录

## FilamentAdmin 第一版边界：

第一版不要一次性做成完整业务平台，而是先做"可安装、可登录、可扩展、可开发业务模块"的后台 MVP。

- 第一版优先实现：后台登录、管理员、角色权限、菜单管理、系统配置、操作日志、附件上传、软删除、基础导出、统一 API 规范、本地插件中心、插件配置入口、插件启停状态、插件索引展示。插件体系支持双轨制：工具型插件（OSS/短信/支付等）住 `vendor/`，业务模块型插件（商城/官网等）解包到 `Modules/`，两套机制统一在插件中心管理。
- 后台权限要区分两类：一类是 Laravel / Filament 后台管理员、运营、编辑、审核等角色权限；另一类是前台用户登录、访问受限内容、查看权益这类前台用户权限。两套权限不要混在一起设计。
- 扩展包只解决通用能力，不承担核心业务逻辑。权限、媒体库、上传、富文本编辑器可以优先用成熟 Laravel / Filament 扩展。
- 数据权限（按部门/数据范围行级过滤）第一版不实现，仅在 Resource 基类预留 `scopeQuery()` 方法约定，业务模块自行重写。
- 演示环境放到第二版规划，第一版不提供。

### 技术选型清单

#### 权限体系

- **底层**：`spatie/laravel-permission`（12.9k stars，Laravel 生态权限标准包）
- **Filament UI 层**：`bezhansalleh/filament-shield`（基于 Spatie，为 Filament 自动生成 Policy 和权限管理界面，不是两套系统）
- **权限粒度**：Action 级别，覆盖 `viewAny / view / create / update / delete / forceDelete / restore / reorder` 等所有 Filament 标准操作
- **超级管理员**：通过 `super_admin` 角色 + `Gate::before()` 拦截实现，数据库标记方式，可配置角色名
- **数据权限**：第一版不做，预留 `scopeQuery()` 方法约定

#### 操作日志

- **日志记录**：`spatie/laravel-activitylog`（5.8k stars，自动记录 Model 变更 before/after diff）
- **Filament 展示**：`pxlrbt/filament-activity-log`（社区主流，Filament 面板内查看日志与 diff）
- **分表策略**：操作日志用 `activity_log` 表，登录日志单独建 `login_logs` 表（字段不同）
- **清理策略**：内置 `php artisan activitylog:clean --days=N` 命令，配合 Laravel 定时任务，超过 N 天自动清理
- **记录范围（重要）**：默认采用 **opt-in 策略**——只对"后台 Filament Action 触发的操作"（如 Resource 的创建/更新/删除/启停）自动记录，普通业务 Model 的写入**不自动记录**。业务 Model 需要记录变更时，开发者主动在 Model 上 `use LogsActivity` Trait 并配置 `getActivitylogOptions()` 启用。
  - **为什么不全量记录**：`spatie/activitylog` 默认对所有 Model 启用会让高频写入表（订单、消息、计数等）每次更新都产生一条 JSON diff 记录，长期会成为性能黑洞和存储黑洞。opt-in 策略把"是否值得记录"的判断交给业务开发者。

#### 媒体库 / 附件管理

- **包**：`spatie/laravel-medialibrary`（6.1k stars）+ `filament/spatie-laravel-media-library-plugin`（官方出品，550 万次下载）
- **存储策略**：默认本地磁盘；云存储（OSS/S3 等）以插件形式扩展，不进入主系统
- **能力**：支持文件与 Model 关联、Collection 分组、图片自动生成缩略图、文件排序、文件复用

#### 系统配置管理

- **包**：`spatie/laravel-settings`（强类型 PHP 类定义配置）+ `filament/spatie-laravel-settings-plugin`（官方出品，Filament 配置页生成）
- **分组方式**：每个配置模块对应一个 Settings 类（`GeneralSettings`、`MailSettings`、`SmsSettings` 等），插件可注册自己的 Settings 类
- **缓存**：内置 Redis/Cache 支持，高频配置读取不查库
- **类型支持**：文本、开关、下拉、图片等由 Filament 表单组件决定，底层强类型 PHP 属性约束

#### API 规范

- **认证方式**：`laravel/sanctum`（Laravel 官方内置，面板用 Session 认证，对外 API 用 Bearer Token）
- **路由分离**：后台 API 走 `/admin/api`，业务 API 走 `/api/v1`，两者路由文件独立管理
- **版本管理**：URL 前缀 + 目录隔离方案（`app/Http/Controllers/Api/V1/`），Laravel 官方和社区均无成熟的版本管理专用包，原生路由前缀是最广泛的做法
- **版本选择理由**：开源项目一旦有用户依赖 API 结构，不加版本号的升级代价极大；加 `/v1` 前缀工作量极小但长期收益高

##### `/api/v1` 响应格式规范

Laravel 无官方响应格式规范包，社区也无事实标准包。选择直接用 Laravel 自带能力（API Resource + 默认异常处理器），补一个自定义业务异常类，这是 Spatie、Laravel Nova 等主流项目的共同做法。

**后台 `/admin/api`**：使用 Laravel 自带默认格式，不额外约定。

**业务 `/api/v1`** 统一格式如下：

```json
// 成功 - 单对象 (HTTP 200)
{ "data": { "id": 1, "name": "张三" }, "message": "ok" }

// 成功 - 列表+分页 (HTTP 200)
{ "data": [...], "meta": { "current_page": 1, "last_page": 5, "per_page": 15, "total": 75 } }

// 失败 - 验证错误 (HTTP 422)
{ "message": "数据验证失败", "errors": { "phone": ["手机号格式不正确"] } }

// 失败 - 业务/认证/权限/404 错误 (HTTP 400/401/403/404)
{ "message": "Token 已过期，请重新登录", "code": "TOKEN_EXPIRED" }
```

字段约定：
- `data`：成功时的业务数据，由 Laravel API Resource 自动包裹
- `message`：人类可读提示，前端可直接 toast 展示
- `code`：**字符串**业务错误码，仅在错误响应中出现，供前端细分处理（如区分 `TOKEN_EXPIRED` / `TOKEN_INVALID`）；HTTP 422 验证错误不需要 `code`
- `errors`：422 时的字段级错误，字段名与表单字段对应
- `meta`：分页信息，`->paginate()` 自动生成

实现方式：
- 成功响应：Controller 返回 API Resource，`data` 自动包裹
- 错误响应：`app/Exceptions/Handler.php` 统一捕获，始终返回 JSON（避免未捕获异常返回 HTML）
- 业务错误：自定义 `BusinessException` 携带 `code` 字段，Handler 统一渲染
- 分页：直接使用 `->paginate()`，Laravel Resource Collection 自动生成 `meta` + `links`

##### 错误码注册规范

业务错误码 `code` 字段是字符串常量，需要全局唯一以避免插件之间冲突。FilamentAdmin 约定：

- **核心错误码清单维护在 `docs/reference/error-codes.md`**，按字母序列出所有保留码、含义、对应 HTTP 状态
- **核心保留前缀**：`AUTH_*`、`TOKEN_*`、`PERMISSION_*`、`VALIDATION_*`、`SYSTEM_*`、`PLUGIN_*` 由核心保留，插件禁止使用
- **插件错误码命名空间**：插件错误码必须以 **插件 ID 大写 + 下划线** 作为前缀，例如 `OSS_BUCKET_NOT_FOUND`、`MALL_ORDER_PAID`。插件 ID 取自 `Filament\Contracts\Plugin::getId()`，与 Composer 包名解耦但要求唯一
- **错误码注册接口**：插件在 ServiceProvider `boot()` 中通过 `ErrorCodeRegistry::register(pluginId, [code => description])` 注册自己的错误码，核心在启动时检测前缀冲突并在 `php artisan filament-admin:doctor` 命令中报告

#### 插件与模块系统

- **业务模块型插件底层**：`nwidart/laravel-modules`（1553 万次下载，6.1k stars，Laravel 模块化事实标准）
- **工具型插件底层**：标准 Composer Package + `spatie/laravel-package-tools`（1.37 亿次下载，ServiceProvider 编写事实标准）
- **插件启停**：工具型走数据库标记 + `AppServiceProvider`；模块型走 `nwidart` 的 `modules_statuses.json`
- **插件类型声明**：`composer.json` `extra.filament-admin.type` 字段，`package`（工具型）或 `module`（业务模块型）

#### 登录安全

- **登录频率限制**：Filament 5.x 内置（每分钟 5 次尝试，基于 `danharrin/livewire-rate-limiting`），无需额外配置
- **二步验证（2FA/TOTP）**：`stephenjude/filament-two-factor-authentication`（19 万次下载，Filament 生态 2FA 最主流方案，支持 TOTP + Passkey + Recovery Code）
- **文件上传安全校验**：第一版暂不做（类型白名单、病毒扫描等），后续按需补充

## 核心扩展点清单

第一版提供的可重写/可监听扩展点（开发者无需 fork 核心代码即可定制）：

**基类与 Trait**：
- `FilamentAdmin\Core\Resources\BaseResource`：所有 Resource 推荐继承，预留 `scopeQuery()` 方法供数据权限重写
- `FilamentAdmin\Core\Plugins\ModuleFilamentPlugin`：业务模块型插件基类，封装 `discoverResources/discoverPages/discoverWidgets`
- `FilamentAdmin\Core\Concerns\HasDataScope`：Trait，业务 Model 接入数据权限过滤（第一版仅签名占位，实现在第二版）

**Filament Panel 钩子**：
- `AdminPanelProvider` 中所有 `->plugin(...)` 注册点都可被用户在自己项目里重写或追加
- 提供 `FilamentAdmin::registerNavigationGroups([...])` 静态方法供插件注册菜单组

**事件**：
- `PluginEnabled` / `PluginDisabled` / `PluginInstalled` / `PluginUninstalled`：插件生命周期事件
- `AdminLoggedIn` / `AdminLoggedOut` / `AdminLoginFailed`：登录事件（驱动登录日志写入，也供二开监听）
- `SettingsUpdated`：配置变更事件（缓存失效钩子）

**契约（Contract）**：
- `FilamentAdmin\Contracts\ErrorCodeProvider`：插件实现此接口可贡献业务错误码
- `FilamentAdmin\Contracts\MenuProvider`：插件实现此接口可向后台菜单注入条目

> 完整扩展点参考详见 `docs/development/base-classes.md`（待写）。

## 测试与质量门槛

作为开源框架底座，第一版必须配齐基础质量保障设施：

- **测试框架**：`pestphp/pest`（Filament 官方文档默认推荐，社区主流），核心模块单元测试覆盖率目标 **60%+**，关键安全路径（登录、权限校验、插件启停）100% 覆盖
- **静态分析**：`larastan/larastan`（Laravel 生态 PHPStan 标配），CI 中要求 **level 6 通过**
- **代码风格**：`laravel/pint`（Laravel 官方，PSR-12 基础），所有 PR 必须通过 `pint --test`
- **CI/CD**：GitHub Actions，PR 触发以下流水线：
  - PHP 8.3 / 8.4 矩阵跑 Pest 测试
  - Pint 风格检查
  - Larastan 静态分析
  - 文档构建检查（确保文档链接不死）
- **依赖安全**：定期跑 `composer audit` 检查依赖 CVE
- **插件开发者要求**：插件如希望进入官方插件市场索引，必须提供基础 Pest 测试套件并通过 Larastan level 5
